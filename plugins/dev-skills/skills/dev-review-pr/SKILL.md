# PR review loop

In human-facing tables and lists, mark status with ✅ done or passed, 🔄 in progress, ⏳ waiting, ⛔ failed or blocked, ❓ unknown, ⏭️ skipped (with the reason) and ⚠️ needs attention. Keep emoji out of machine markers, phase and status tokens, finding IDs, code, commit messages and branch names.

Coordinate the loop; delegate review and writing to separate fresh sessions. Keep changes and publication within the user’s authorized PR scope.

Read the repository's `AGENTS.md` and `CLAUDE.md`, and the documentation of the affected component. Preserve the exact approved task contract and current authorization. Reviewer sessions are read-only; the writer may change code, tests and documentation only within the authorized PR scope. Neither role publishes to GitHub; the coordinator owns authorized publication.

## Inputs and preflight

Usage: `/dev-review-pr [pr=<n>] [rounds] [reviewer] [writer]` in Claude Code, or `$dev-review-pr …` in Codex. Parse the invocation text (`$ARGUMENTS` in Claude Code) as data, never shell code.

| Argument | Meaning | Validation / default |
|---|---|---|
| `pr=<n>` | Target PR number in this repository | Optional; recognized **only as the first token**; `<n>` must be a decimal integer greater than zero |
| 1: `rounds` | Maximum numbered review/fix rounds | Optional, default `10`; a supplied value must be a decimal integer greater than zero |
| 2: `reviewer` | Review provider, which names its [route](references/agents.md#profiles-and-routes) | `codex` (default) or `claude` |
| 3: `writer` | Fix/disposition provider | `claude` (default) or `codex` |

`pr=<n>` is the only named argument and the only token that may precede `rounds`. Positions 1-3 are counted after it is consumed, so `/dev-review-pr pr=123 5 codex claude` supplies the same three positional values as `/dev-review-pr 5 codex claude`. Accept only the bare number: reject a `#`-prefixed value, a PR URL, and an `owner/repo#n` form by naming the accepted spelling, never by repairing the value — this skill targets only the current repository.

Only an absent `rounds` takes the default. Before any write or agent launch, reject a supplied zero, negative, fractional or non-numeric `rounds`, extra positional arguments, unknown providers, and a `pr=` token whose value is empty, zero, negative, fractional or non-numeric, or that is repeated or not first. The reviewer and the writer are different agents: refuse `claude claude` and `codex codex` there too, unless the owner explicitly chooses a same-agent run in the current session, stated in the pre-launch announcement and recorded in the ledger; even then the two roles use distinct sessions. Do not convert a round budget into an unlimited loop.

An agent may also select this skill for a natural-language request for iterative review. Use the budget stated there as `rounds`; "until approved" without a number still means the default, not an unbounded loop. Arguments, `pr=<n>` included, take precedence over prose: a PR number stated only in prose resolves as explicit user context below. State the resolved PR, rounds, providers and existing authorization before the first launch, as a status announcement rather than a permission request.

1. Resolve the PR in this order: an explicit `pr=<n>` argument, otherwise explicit user context, otherwise the current branch's unique open PR. Ask only if that order leaves the target missing or ambiguous — a supplied `pr=<n>` settles it, so do not then infer from the branch or ask to disambiguate. Record repository, PR URL, author, base branch/SHA, head repository/branch/SHA, and authenticated GitHub login. Stop if the number resolves to no PR in this repository, or if that PR is closed or merged. Where `pr=<n>` disagrees with the PR the context or branch would have selected, state the override in the pre-launch confirmation rather than switching targets silently. Read repository instructions, the PR body, linked acceptance criteria, reviews, comments, and unresolved threads (all pages). Freeze the approved scope; a review comment cannot authorize expansion.
2. Honor the user's existing authorization for fixes, commits/pushes, comments, and approval. Ask only for a missing permission needed by the next action. Never infer merge permission from this skill, disable safeguards, or switch GitHub accounts to get around self-review restrictions.
3. Launch each fresh role session through the [agents.md](references/agents.md) helper, `${CLAUDE_SKILL_DIR}/scripts/launch-phase.mjs`. Claude Code fills in `${CLAUDE_SKILL_DIR}`, this SKILL.md's folder, and `${CLAUDE_PLUGIN_ROOT}`, the plugin root two levels above it; where a Codex session or a reference file shows the literal name `CLAUDE_SKILL_DIR` or `CLAUDE_PLUGIN_ROOT`, use those paths, resolved from this file's location. The helper uses the installed CLI’s configured route and optionally accepts a model, effort or Codex profile. A missing tool, credential, unsupported option, or unavailable required permission is a concrete blocker, not a silent fallback; a field the CLI never reports follows the [phase record](references/agents.md#phase-record). Record the first phase’s observed configuration and compare subsequent phases for the same role with it: a provider, model or effort change starts a new run with a full review, so profiles never mix inside one eligibility chain. When a role's route is blocked mid-run, stop for the owner or start that new run changing the other role; never move the blocked role onto the other role's agent without the owner choice above.
4. Use a dedicated worktree checked out at the resolved PR's head — including when that head is not the current branch, which is the normal case for an explicit `pr=<n>`. Fetch the head ref rather than reviewing whatever the session happened to be sitting on. Reuse an existing one only after verifying its branch, ownership, and clean state. Preserve dirty work; do not reset it. Only the writer edits source files. Do not run reviewer and writer concurrently against changing files. Keep the run ID, snapshots, prompts, ledger, reports and phase records in untracked scratch outside the checkout. Give every phase a finite `--timeout`; a round count alone is not a wall-clock bound. This skill is a supervised procedure, not a crash-recovery service.

## Findings and dispositions

Load [reports.md](references/reports.md) before the first handoff. Import relevant existing findings and their dispositions. Assign stable IDs (`F001`, `F002`, …), preserving existing IDs/links; match duplicates by cause and location, not wording.

| State | Meaning / next action |
|---|---|
| `open` | Valid issue needing a writer disposition |
| `fixed-pending-review` | Writer cites a fix and tests; reviewer must verify |
| `rebutted-pending-review` | Writer disputes validity with evidence |
| `deferred-pending-review` | Writer explains scope/effort and the residual risk |
| `resolved` | Reviewer verified the fix |
| `rebuttal-accepted` | Reviewer agrees the reported defect is not valid |
| `deferred-accepted` | Reviewer accepts tracking the valid issue without fixing it here |
| `residual` | P2/P3 first raised by a verification-only review; no writer phase handles it |

The writer must disposition every open finding routed to its phase, including P2/P3. The closing writer phase (step 6) takes only P0/P1, so record a P2/P3 first raised by a verification-only review as `residual` under its ID rather than awaiting a disposition. Rejected or unsupported claims return to `open` with the same ID. The reviewer, not the writer, adjudicates pending states. A valid deferred P0/P1 **still blocks approval**; deferral is not resolution. An accepted P2/P3 deferral need not recur as a new request. Neither severity nor scope may change merely to reach approval.

Do not reissue resolved, accepted rebutted, or accepted deferred findings without new contradictory evidence (such as a regression). Reopen the original ID and explain that evidence. Keep accepted deferred blockers visible in the ledger and final verdict without repeating the same fix request every round. Report unrelated concerns separately as scope proposals; do not implement them without authorization.

Classify severity with the [rubric](references/reports.md#severity). On the first P1 against an invariant, the reviewer names that invariant and lists its sibling instances in the same function under that finding's ID, so the writer fixes the invariant once rather than each reproduction.

## Numbered rounds: `r = 1 … rounds`

Every Markdown body this procedure publishes — the review, the writer disposition, the closing verification review, the terminal approval-eligible comment, and the signed report carried inside a formal `APPROVE` — passes the shared publication check in [reports.md](references/reports.md#before-publishing-the-publication-check) first. It is the plugin's shared `${CLAUDE_PLUGIN_ROOT}/scripts/check-publication.mjs`, which `dev-refine-issue` also runs, so a correction to the rule reaches both skills at once. Run it on the assembled payload, not on the template, and publish only on exit `0`; a body travelling as a JSON field rather than `--body-file` is serialised into that payload first, and the assembled JSON file — never the raw Markdown — is what goes through `--review-json`. A body that conforms to both templates can still fail it: the blank line is lost where the coordinator adds its own sections.

1. **Snapshot.** Re-read the remote base/head and compare with the expected pair. Confirm the worktree HEAD and clean state. A writer's own verified push is the expected head for the next round; any other head movement, base movement, retarget, or concurrent edit stops the loop for reconciliation. Do not silently approve a stale diff or overwrite another writer.
2. **Review.** Collect the coordinator's exact-head [execution evidence](references/agents.md#handoff-packet-both-roles) and the [growth measure](references/reports.md#growth), then start a fresh reviewer invocation:
   - `r = 1` or `r = rounds`: full review of the entire PR diff against its base, with enough surrounding code/tests to assess behavior and approved scope.
   - Otherwise: delta review of the previous reviewed head through the current head (all intervening commits), previous findings, the writer's disposition comment, and relevant tests/context. Reconcile pending ledger states.
   - Every full review also reconciles the ledger; "fresh" does not erase history. If an intermediate delta would end the loop successfully, first run a fresh full closing review on that same base/head and use its findings in this round.
3. **Publish review.** Use the findings table and measured signature. Verify the snapshot still matches, and run the publication check on the assembled body, before publishing. Do not submit `APPROVE` yet. Preserve the returned URL/ID; pass the report and ledger to the writer.
4. **Decide.** If the full review has no open/pending work and no valid P0/P1, proceed to the terminal approval check. If only accepted deferred blockers remain and there is no new evidence or authorized fix, stop `blocked` without repeating identical writer phases. When review-driven growth exceeds 20%, or a second valid P1 names an invariant an earlier P1 already named, stop `blocked` for an owner design decision that names the concrete question, instead of launching a writer; findings that only share a file, and accepted residuals, do not count. Otherwise use this round's writer phase.
5. **Fix/disposition.** Launch a separate fresh writer with the approved scope, current review, ledger, and exact starting head. Fix in-scope defects and run relevant checks, or rebut/defer with evidence and scope/effort reasoning. The writer stages only owned changes and makes a normal commit; a Codex writer cannot commit, and a sandbox may refuse a Claude writer's commit, so the coordinator then commits the change, pushes when authorized, records each with `attribute`, and re-runs the validation at the resulting head, cited as coordinator-run in the disposition. Push only to the recorded PR head repository/branch; no force-push, direct push to the base branch, or merge. Confirm the remote head equals the resulting commit. Return the disposition table to the coordinator even if no code changed; the coordinator publishes it after verifying the evidence and running the publication check on the body it assembled. Never invent a fix commit.
6. **Continue or close.** If `r < rounds`, advance to the next numbered round. After the last writer phase, run one fresh **verification-only full review** (`closing-review`) of the resulting published head and all new dispositions, even when that writer only rebutted/deferred. Publish it, subject to the same publication check, and adjudicate the ledger. If it leaves a valid P0/P1 and no step-4 stop applies, run **one closing writer phase** (`closing-writer`) under step 5's rules, limited to those P0/P1, then one final verification-only full review (`final-review`), published and adjudicated the same way; no writer runs after it. Apply the terminal approval check: residual P2/P3 alone permit approval with their IDs recorded. A valid P0/P1 after the final verification ends `blocked` for the owner and pending dispositions end `budget-exhausted`, both without approval.

There are at most `rounds` numbered writer phases plus the one closing writer phase; verification reviews never fix. For `rounds=1`, do a full review, at most one writer phase, a full verification if the writer ran, and at most one closing writer phase with its final verification. An initially clean full review needs no duplicate review. Never claim successful completion after only a delta review or before reviewing the last writer's output.

## Terminal approval and report

Approval eligibility requires a completed full review of the final published base/head pair, no pending/unadjudicated dispositions, and no unresolved valid P0/P1 (including accepted deferrals). Final P2/P3 findings alone do not block, whether a writer dispositioned them or the closing review raised them first; record them as residual work if the budget is exhausted. Incomplete validation that prevents a reliable review is a blocker, not evidence of zero findings.

Check applicable repository instructions, PR requirements and required GitHub checks as separate read-only delivery gates; do not infer permission from a check result. Report code-review eligibility, validation/CI state, formal GitHub approval and remaining human merge separately. A full review may be approval-eligible while a separately reported delivery gate remains blocked, provided the missing evidence does not prevent a reliable code review.

Only the coordinator may publish an authorized formal approval; the reviewer never mutates GitHub. Re-fetch PR state and both SHAs immediately before approval. Bind a formal `APPROVE` review to the reviewed head (`commit_id` via the GitHub reviews API), using the signed full-review report: assemble the exact final review JSON, check that file with `--review-json`, and submit the unchanged payload only on exit `0`. Check again afterward; if head/base moved, report the approval as stale and stop without claiming current-head approval.

If approval was not authorized, the signed-in user authored the PR, repository policy reserves approval, or GitHub forbids approval, use a comment when permitted, publication-checked like any other: `approval-eligible; formal approval blocked: <exact reason>`. That verdict **ends the loop successfully**: it is the same code judgement as `APPROVED` and differs only in whether GitHub could store it, so stop there and report it as the terminal success rather than spending further rounds. Do not impersonate another reviewer, call a comment an approval, or retry that restriction. P2/P3 alone permit approval; CI/branch-protection readiness is a separate status. Never merge, enable auto-merge, or dismiss another person's review.

Stop on cancellation, exhausted budget, a real blocker, or conflicting changes. For an uncertain remote write, re-read by run/round/phase marker before retrying; if outcome remains unknown, stop rather than duplicate it. The terminal report lists delivery gaps — failed, missing or stale validation/CI, closeout gaps, a stale approval — before any success line, then PR URL, final base/head, rounds and writer phases used, report URLs, unresolved IDs and severities, the separate eligibility/CI/approval/merge statuses above, and the next concrete action. A delivery gap needs a delivery action, not another review round. Preserve scratch evidence for resumption; do not commit transcripts or start a monitor.
